# AI-augmented Software Composition

This repository aims to be a collection of topics, practices and templates, leading into a model of how software could be composed in a modern, AI-augmented way using generative AI tooling. The content describes a framework and collects practices of how to best give inputs to language models (LMs) and generative AI coding agents. 

![CC-BY-SA40](https://licensebuttons.net/l/by-sa/4.0/88x31.png)


# Overview

The model augments the established software development lifecycle and delivery processes by usage of GenAI coding agents, wherever applicable and appropriate. While most of the tools in the generative AI coding space focus on the actual generation of code, this content here does not solely focus on code or specific aspects of managing a codebase. It aims at covering a wider range of topics from requirements engineering, software architecture and design to software development. Therefore it is based on [Software Engineering Body of Knowledge (SWEBOKv4)](https://ieeecs-media.computer.org/media/education/swebok/swebok-v4.pdf) and the ongoing work of [specification-driven development](https://speckit.org/).

It applies to Software Architecture, Design, Construction, Testing and Maintenance, in varying degrees of support, aiming to bridge the gap between what has become known as „Vibe Coding“ and professional software development beyond the MVP stage.

# Rationale

AI coding agents autonomously plan, execute, and refine software tasks, reshaping traditional software development workflows.
The integration of AI agents introduces new architectural patterns emphasizing modularity, tool orchestration, and iterative feedback loops. Software design processes must adapt to AI-assisted code generation, refinement and complex workflow management. SWEBOKv4 provides a foundational framework to analyze and integrate AI agentic programming paradigms.

Human oversight is required to address the risks introduced by GenAI. However, it must be balanced with AI autonomy to maximize utility.

# Objectives and Scope

If largest parts of code are generated by AI, the focus of human work shifts to controlling both 
- input to AI (requirements of any kind) and 
- output from AI (regarding software verification and validation).

The primary objective is to have a proven and stable process for collaboration between humans and AI on software creation, with focus on professional, enterprise-grade software development practises.

In targeted scenarios, at least 90% of code and configuration in a software development project is produced by AI.
Therein, AI augments relevant parts of the Software Development Lifecycle (SDLC), leading to fundamental changes in the way we produce working software (regarding organization of teams, collaboration processes, estimations and more).

# Affected parts within the SDLC

Obviously, generative AI can assist in many aspects of the Software Development Lifecycle. This model covers only some knowledge areas, and aims to support up to a certain level.

| SDLC Knowledge Area | Targeted level of augmentation | Example |
|---------------------|-----------------------|---------|
| Requirements Engineering | 25% | AI should assist in completing requirements specifications |
| Software Architecture    | 50% | AI should assist on research of best practices, architecture patterns and producing architectural requirements |
| Software Design          | 50% | AI should assist of producing working sketches of software module designs |
| Software Construction    | >=90% | The majority of code should come from a Generative AI source, derived from proper requirements |
| Software Testing         | 25% | AI should assist in sketching out new unit test and integration test code, but not touch existing test surface |
| Software Maintenance     | >=75% | AI should assist in defect fixing and refactoring, properly guarded by requirements |

# Guiding principles

The foundation of guiding principles below is that both structured requirements and meaningful examples are needed to guide the LM toward the desired outputs. Especially non-functional requirements and technical boundaries are required ot keep output within intended constraints.

| Principle | Explanation |
|-----------|-------------|
| Context Is Everything | Requirements must be precise and extensive, as they are the main high-level context that can be given to a LM. |
| Provide Just Enough Context | Keep prompts lean. Let AI process only the minimum input that predictably leads to working results. |
| Context Is the Journey | Move AI agents from requirements to code through every relevant SDLC checkpoint so code prompts carry the full narrative. |
| Align Delivery With Architecture | Inject requirements in an order that mirrors the architecture so generated outputs compose cleanly. |
| Provide Working Examples | Give examples or templates at each step so the LM can pattern-match the desired outcome. |
| Treat Rework as Waste | Post-processing code might happen, but use each occurrence as a signal to tighten requirements or prompts. |
| Maintain Context Traceability | Track where each requirement shows up in the codebase so humans and LMs can rehydrate original intent. |

## Context Is Everything

Providing the right context is key to getting good results from a language model. This challenge is well-known, and being answered in different ways. In particular frontier language models might offer a huge contexts (e.g. 1M tokens), but the outcome is not only determined by size, but also by quality of inputs.

Inputs to LM should be
* a concise and un-ambiguous domain language, which is used throughout the rest of the context
* well-written high-level requirements, ideally broken down hiearchically
* well-structured functional requirements, e.g. on the level of user stories
* non-functional requirements that affect different parts of the codebase (e.g. maintainability)
* technical constraints regarding code language, build system, packages, frameworks, 3rd party libraries etc.

The mix of above inputs should be the curated source-of-truth, to keep downstream prompts aligned.

## Provide Just Enough Context

GenAI agents might handle this topic differently according to their capabilities. To avoid overusing the context and providing too much information (and thus confusing the LM), this principle is about providing the LM only what it needs for the task at hand.

This includes the step-by-step selection and processing of functional requirements, one-by-one, while referencing the relevant non-functional requirements and technical constraints.

## Context Is the Journey

Many GenAI coding agent already provide this functionality. A working pattern is to start with the initial functional requirements, adding non-functional requirements and constraints. Agent modes can then provide an implementation plan, adding this to the context alongside a task list of things to be implemented.

This concept is taken further by applying steps of the SDLC to continuously refine and improve the implementation, yielding higher success rates. The journey could include
* initial requirements
* software architecture patterns to be used
* software design principles to be used
* a concrete software design to be worked out (resembles the agent's implementation plan)

The goal is for the coding task to have access to the full narrative. 
This approach can also support the review, as the LM follows the same journey a human team would.

## Align Delivery With Architecture

In a classic coding scenario, human coders would likely not start from scratch with the most complex requirement, or a function that requires many foundational code modules to be present before. A certain amount of work first goes into setting up the build system, choosing 3rd party libraries and frameworks, setting up testing structures, etc.

In the same direction, the delivery of functional requirements and technical constraints should align to the architecture so that a solid foundation is created by the AI. This foundation can then serve as blueprint example code for the implementation of subsequent requirements.

This is also related to an early implementation of cross-cutting concerns, e.g. logging, monitoring, security, modularity, and more, so that newly generated artifacts integrate without costly (and potentially error-prone) reshaping.

## Provide Working Examples

The point of this principle is to enrich prompts with examples that illustrate structure, design principles and completeness.
LMs appear to be more successful if output can be derived from an existing example structure that is similar enough. This can apply not only to code, but also to architectural patterns and design descriptions. Valid examples can also be given by architectural diagrams such as C4/UML, or as data structures (e.g. using protobuf, GraphQL type system etc.)

## Treat Rework as Waste

This concept is based upon principles of Lean Thinking [LEAN]. Lean introduces different types of waste which must be eliminiated in order to optimize the process. In this sense, any kind of manual rework of code (i.e. re-arranging modules, structures, fixing code etc.) is considered waste.

Instead of investing human time to fix AI output, this principle is about refining all inputs (requirements, acceptance criteria, guardrails, prompts etc.) to prevent the same kind of waste from being generated again.

## Maintain Context Traceability

This principle is about maintaining an auditable map from requirement to generated artifact to validation result so both humans and LMs can quickly trace back to the original intent when changes (or question, e.g. in case of errors) arise. This can be made possible by assigning unique identifiers to requirements and asking the LM to output references in code as comments.
